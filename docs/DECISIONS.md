# 設計上の判断と仮定（DECISIONS）

要件定義書に明記がない点や、要件どうしの調整が必要だった点について、どう判断したかを記録します。
運用前に発注者の確認が必要なものには **【要確認】** を付けています。

| # | 判断 | 理由 |
|---|---|---|
| 0-1 | 2つの要件定義書（電子契約システム／Zelnora app）を、1つのリポジトリ（pnpm モノレポ）で実装した。`apps/sign`（電子契約）、`packages/zelnora-core`・`apps/zelnora-gas`・`apps/zelnora-web`（Zelnora）。 | 両方の要件定義書が同時に渡され、Zelnora 側の要件（1.2・12章）が電子契約システムとの連携を前提にしているため。技術構成が異なる（Vercel＋Supabase／Apps Script＋スプレッドシート）ので、アプリは分けたまま同じリポジトリに置いた。 |

## 1. 電子契約システム（apps/sign）

### 1.1 技術構成（要件3章からの変更点）

| # | 判断 | 理由 |
|---|---|---|
| 1-1 | サーバーからのDBアクセスは supabase-js ではなく、PostgreSQL への直接接続（`pg`、Supabase の Transaction pooler）で行う。Supabase は「管理者の認証（パスワード＋TOTP）」と「ファイル保存（Storage）」に使う。 | 署名の確定を1つのトランザクションで行う必要がある（4.6）ため。また、同じ処理をローカルのPostgreSQLで結合テストできる。 |
| 1-2 | テーブルへの書き込みはすべてサーバー経由とし、`authenticated`（管理者）には参照のみを許可した（RLSのポリシーは SELECT のみ）。`anon` には何も許可しない（検証用の関数 `verify_document` のみ実行可）。 | 「管理者の権限でもAPIから更新・削除できない」（受け入れ基準4）を確実にするため。 |
| 1-3 | 署名済みの契約・確定版PDF・タイムスタンプ・監査ログの変更・削除は、RLSに加えて **トリガー** で禁止した。トリガーは service_role や DB所有者にも適用される。 | service_role は RLS を迂回できるため、RLSだけでは要件4.6・4.7を満たせない。 |
| 1-4 | PDF生成は `pdf-lib`。日本語フォントは Noto Sans JP（Regular・Bold の TTF を `apps/sign/assets/fonts` に同梱。SIL OFL）を埋め込む。pdf-lib のサブセット化では日本語のグリフが欠けるため、**HarfBuzz（subset-font）で使用文字だけのサブセットを作ってから埋め込む**。OpenTypeのレイアウト機能は外した（欧文中の数字が全角幅になる不具合の回避）。 | フォントを必ず埋め込み、ファイルサイズも抑えるため（PDFは約150〜300KB）。 |
| 1-5 | RFC 3161 のクライアントは `pkijs`/`asn1js` で実装した。応答のハッシュ値・nonce・署名を検証する。開発・テスト用に内蔵のTSA（自己署名・証拠力なし）を用意し、`TSA_URL=dev` で使える（本番では起動時にエラー）。 | 外部TSAに依存せずにテストできるようにするため。 |

### 1.2 データモデル（要件6章からの変更点）

| # | 判断 | 理由 |
|---|---|---|
| 1-6 | `documents` にはタイムスタンプを持たせず、追記専用の `document_timestamps` に分けた。`timestamp_jobs`（再試行キュー）は更新可能な別テーブル。 | `documents` は更新不可（6章）だが、TSAに失敗した場合は後から付与する（4.6-4）必要があるため。 |
| 1-7 | `access_tokens` にはトークンのハッシュ（照合用）に加えて、**アプリ側の鍵（`TOKEN_ENCRYPTION_KEY`）で暗号化したトークン** を保存する。 | 「データベースにはトークンのハッシュ値のみを保存」（4.4）と「URLの再コピー」（4.8）を両立させるため。DBだけが漏れてもURLは復元できない。【要確認】ハッシュのみに厳密に従う場合は、再コピーの代わりに再発行（旧URLは無効）とする必要があります。 |
| 1-8 | 監査ログの `seq`（連番）はトリガー内で排他ロックを取って採番し、`prev_hash` とともに計算する。整合性チェックは連番の欠落（削除）・直前のハッシュとの不一致・内容の改ざんを検知する。 | 同時に書き込まれてもチェーンが分岐しないようにするため。 |
| 1-9 | 変数（差し込み項目）のキーは「表示名」そのもの（例 `{{受講者氏名}}`）とした。システム変数 `{{発注者名}}`・`{{契約ID}}`・`{{契約締結日}}` を用意した。 | 要件4.2の記法に合わせ、テンプレートを直感的に編集できるようにするため。 |
| 1-10 | 「期限切れ」はDBの `contracts_view.effective_status` で即時に判定し、定期処理でも `status` を更新する。 | 定期処理の実行間隔に関係なく、期限切れのURLで本文を表示しないため（受け入れ基準7）。 |

### 1.3 署名フロー

| # | 判断 | 理由 |
|---|---|---|
| 1-11 | 署名URLは `https://…/s#<トークン>` とし、**トークンはURLのフラグメント**に置く。画面は受け取ったトークンをヘッダー（`x-sign-token`）でAPIに送る。 | フラグメントはサーバーに送られず、アクセスログやRefererに残らないため（5章「トークンや秘密情報をログに出力しない」）。 |
| 1-12 | 本文は本人確認（OTP）の **後** にだけ返す。URLだけでは件名と発注者名しか分からない。本人確認後はHMAC署名付きのCookie（1時間・`/api/sign` 限定・トークンのハッシュに紐づく）で状態を持つ。URLを無効化するとセッションも使えなくなる。 | URLが転送・漏えいしても契約書の内容が見られないようにするため。 |
| 1-13 | 「URLをコピーして送った」場合、署名者が入力したメールアドレスが、契約に登録されたメールアドレスと一致しなければ確認コードを送らない（登録がない場合は入力されたアドレスで本人確認する）。 | URLを入手した第三者が自分のアドレスで本人確認できないようにするため。 |
| 1-14 | 氏名の一致判定は、全角・半角と空白を無視して比較する（「山田 太郎」＝「山田太郎」）。 | 入力の揺れで署名できなくなるのを防ぐため。 |
| 1-15 | OTPの制限：有効期限10分、5回失敗でロック（30分）、1時間に5回まで・再送は30秒あける。OTPはサーバーの秘密値（`OTP_SECRET`）付きHMACで保存。 | 要件4.5・5章。6桁の総当たり逆算を防ぐ。 |
| 1-16 | 署名後も同じURLで「閲覧・ダウンロード専用」になるが、閲覧には再度の本人確認を求める。署名後でもURLの有効期限を過ぎると表示しない（署名者には確定版PDFをメールで送付済み）。 | 受け入れ基準7を例外なく満たすため。 |
| 1-17 | 確定版PDFに「タイムスタンプの情報を含める」（受け入れ基準8）ため、タイムスタンプは2種類取得する。①**契約内容**（本文・値・署名者・日時の正規化JSON）のハッシュへのタイムスタンプ → 合意締結証明書に時刻・発行元・シリアルを印字、②**確定版PDF全体**のハッシュへのタイムスタンプ → DBに保存し、管理画面から `.tsr` をダウンロードできる（`openssl ts -verify` で第三者が検証可能）。 | PDF自身のハッシュへのタイムスタンプは、そのPDFの中には書けない（書くとハッシュが変わる）ため。PDFへの埋め込み（PAdES）はフェーズ3。 |
| 1-18 | 「1つのトランザクション」（4.6）は、PDFの生成とストレージへの保存の後に、DB側の処理（署名者の更新・documents・監査ログ・契約の確定）をDB関数 `finalize_signature` の1トランザクションで行う形とした。DBの処理が失敗した場合、ストレージには参照されないPDFが残るが、契約は署名済みにならない。 | ストレージとDBをまたぐ分散トランザクションは作れないため。 |

### 1.4 その他

| # | 判断 | 理由 |
|---|---|---|
| 1-19 | **別添のdocx（既存の受講契約書）は受領していない。** 初期テンプレートとして、一般的な受講契約の構成で「AIエンジニア育成マンツーマン講座 受講契約書」を作成し、登録できるようにした（管理画面のボタン、または `pnpm seed`）。【要確認】既存の契約書の文言に差し替え、弁護士の確認を受けてください。特に、受講期間2か月超・5万円超の場合は特定商取引法の「特定継続的役務提供」（パソコン教室等）に当たる可能性があり、クーリング・オフ等の記載が必要になることがあります。 | 受け入れ基準の「既存の受講契約書をテンプレートとして登録」に対応するため。 |

| 1-27 | **既存の契約書の格納**：他の方法で締結済みの契約書（紙のスキャン・他社サービス）をPDFで格納できるようにした（管理画面「既存の契約書を格納」）。契約は `source = 'imported'`・テンプレートなしで作り、原本は `documents.kind = 'original'` として保存する。下書きで作成 → 署名者・原本・監査ログ → 締結済みへ、を1トランザクションで行い、以後は署名済みの契約と同じく更新・削除できない（DBのトリガー）。原本のハッシュにRFC 3161タイムスタンプを付け、検証ページでも照合できる（「格納した時点で存在した」ことの証明であり、締結の事実そのものの証明ではない）。PDFのみ・4MBまで。同じファイルの二重格納は拒否する。 | ご要望「契約書はあるが格納できるようにしたい」に対応。電子帳簿保存法の検索（取引年月日・金額・取引先）も同じ一覧で行えるようにするため。 |

| 1-30 | **Vercel へのデプロイ**：`apps/sign/vercel.json`（Next.js・Cron）と `apps/zelnora-web/vercel.json`（Vite・SPAの書き換え・CSPなどのヘッダー）を用意し、Root Directory を指定するだけでビルドできるようにした（`vercel build` で確認）。PDF用のフォントは Vercel のサーバー関数で確実に読めるよう、アプリ内（`apps/sign/assets/fonts`）に同梱した。環境変数が足りないときは `/login` に足りない名前を表示し、`/api/health` で設定とDB接続を確認できる（値は表示しない）。 | ご要望「Vercel までリンクできるように」。Zelnora の画面は要件では Cloudflare Pages だが、Vercel でも同じように公開できる（どちらも無料枠）。 |

## 2. Zelnora app

### 2.1 構成

| # | 判断 | 理由 |
|---|---|---|
| 2-1 | 業務ロジックはすべて `packages/zelnora-core`（依存ライブラリなしのTypeScript）に置き、①Apps Script（本番）、②ブラウザ内のデモモード、③Node のテスト、の3か所で同じコードを動かす。 | 固定費0円（1.6）でも、ロジックを自動テストで守るため。 |
| 2-2 | 画面はSPA（Vite＋React）で Cloudflare Pages に置き、APIは Apps Script のWebアプリ（`doPost`）。ログインは Google Identity Services の IDトークンを Apps Script 側で検証する（`OAUTH_CLIENT_ID`）。Webアプリは「自分（システムアカウント）として実行」「全員（匿名を含む）」で公開し、認可はすべてAPI側で行う。 | スタッフにスプレッドシートを共有せず、読み書きをアプリ経由に限る（4章）ため。 |
| 2-3 | `VITE_API_URL` を設定しない場合は **デモモード**（ブラウザ内でcoreを動かし、localStorageに保存。サンプルデータ入り・ロールを選んでログイン）になる。 | 設定前でも操作を確認でき、E2Eテストにも使うため。 |
| 2-4 | スプレッドシートへの保存（`SheetsStore`）は、エンティティごとのタブ（1行目＝項目キー）に書く。既存のシートを「データソース登録簿」で指定した場合は、列の対応（項目→見出し）で読み書きし、**対応のない項目はDBスプレッドシートの影のタブ（`_ext_<エンティティ>`）に保存**する。見出しが想定と違うと、そのデータソースへの書き込みを止めてオーナーに通知する（ZN-SET-11）。 | 既存のシートの見た目を崩さずに、アプリに必要な項目を保持するため。 |
| 2-5 | 設定一式（商材・プラン・段階・フォームの対応付けなど）は、DBスプレッドシートの `_settings` タブにJSONで保存し、変更のたびに `settingsVersions` タブへ版を残す。 | 設定の版管理（ZN-SET-12）と、JSONでの書き出し・読み込み（ZN-SET-13）のため。 |
| 2-6 | 書き込みを伴うAPIは `LockService` で直列化する。顧客・商談・提供は `version` を持ち、画面の編集で他の人の更新と重なったら確認を出す（ZN-CUS-05）。 | 同時に30人程度が使う想定（1.6）のため。 |

### 2.2 業務ルールの仮定

| # | 判断 | 理由 |
|---|---|---|
| 2-7 | **売上の計上ルールと基準日（Q-03）は未決のため、商材ごと・プランごとに選べるようにした**（一括／期間按分／分割払い／月額、基準日＝契約日／入金日／提供開始日）。AES（スクール型テンプレート）の初期値は「一括・契約日」。【要確認】経理・税理士の確認後に設定してください。 | 9.1。 |
| 2-8 | 期間按分・分割で割り切れない端数は **初月** に寄せ、消費税は各行で計算したうえで合計が一致するよう **最終行** で調整する。 | 合計金額・税額を契約と一致させるため。 |
| 2-9 | 締めた月に当たる売上予定・返金は、翌月以降の最初の未締めの月に計上する（元の計上月をメモに残す）。 | 9章「あとからの修正は翌月の調整として記録」。 |
| 2-10 | 次のアクションを必須とする段階の種類は「新規・接触・面談・契約手続き・保留」。「成約」は任意（初期値あり）、「登録完了・失注」は不要。 | ZN-SALES-05「進行中の商談は必ず1つ持つ」。成約後は提供側へ引き継ぐため。 |
| 2-11 | 登録フォームの取り込みで、①成約前の商談がある → 保留（5.4）、②商談がまったくない → 「商談なしの登録」として記録し、**提供は作成**してマネージャーに通知、とした。【要確認】 | 5.2の手順4（商談なしの登録として記録し知らせる）と5.4（契約より先に届いたら保留）の両方を満たすため。 |
| 2-12 | 同じ人の判定はメール（正規化：全角→半角・小文字）→電話（数字のみ、+81→0）。候補が複数なら「統合の確認待ち」。 | 5.2の手順3。 |
| 2-13 | 許可ドメインのアカウントで未登録の人は、最も弱い「閲覧者（担当商材なし）」として自動登録する。 | ZN-ROLE-05 とログインのしやすさの両立。 |
| 2-14 | 「閲覧者」はメール・電話を伏せる（初期値）。項目ごとに見せないロールを設定できる。 | ZN-ROLE-03。 |
